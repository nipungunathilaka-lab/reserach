# 1. Executive Finding

TRUE_E2EE: NO

ZERO_KNOWLEDGE: NO

SERVER_CAN_ACCESS_PLAINTEXT: YES

FINAL_ARCHITECTURE_CLASSIFICATION:
Server-mediated encrypted file-transfer architecture with client-side cryptographic signing, receiver-specific key protection, adaptive PFCE encryption, malware inspection, and isolated security processing.

# 2. Actual File Flow

- **Browser**: Reads file, calculates SHA-256 hash, generates RSA-PSS digital signature over the hash and session nonce. Chunks the file and transmits the unencrypted chunks to the Node.js API.
- **Node.js**: Receives chunks, reassembles them into a temporary plaintext file (`os.tmpdir()`), appends transfer metadata, and streams the plaintext file to the FastAPI internal engine.
- **FastAPI**: Receives the plaintext stream. Writes it to a temporary spool to run ClamAV scanning and Data Classification. 
- **PFCE**: Once scanned, the PFCE engine reads the plaintext in dynamic fragments, generates AES/ChaCha keys, encrypts the fragments, and encapsulates the symmetric keys via ECDH or ML-KEM PQC for the designated receiver.
- **Storage**: The fully encrypted `.pfce` zip package is written to disk. The server no longer has access to the plaintext or the wrapped keys.
- **Receiver**: Authenticates and requests download. FastAPI retrieves the `.pfce` package, streams the encrypted fragments back to the client via Node.js, or decrypts them server-side and streams the plaintext to the receiver (depending on the exact download path invoked).

# 3. Key Ownership

- **Signing Key**: Generated in Sender Browser (WebCrypto). Stored in IndexedDB (non-extractable). Server receives only the public SPKI.
- **Content Key (AES/ChaCha)**: Generated by FastAPI (PFCEEngine) during encryption. Wrapped immediately. Discarded from memory.
- **ECDH Keys**: 
  - Receiver Prekeys: Generated by Receiver Browser, public key sent to server.
  - Ephemeral Sender Keys: Generated by FastAPI during encryption.
- **ML-KEM Keys**: Handled by FastAPI UPCE engine or client.
- **KMS Keys**: Server-owned KMS wraps the database encryption keys and long-term secrets.

# 5. Client-Side Cryptography

- **Signing**: Client uses WebCrypto RSA-PSS to sign a canonical transfer manifest.
- **Hashing**: Client calculates SHA-256 in chunks using `hash-wasm`.
- **Key Generation**: Client generates RSA signing keys and ECDH Prekeys.
- **Content Encryption**: **NONE**. The client does not encrypt the file payload.

# 8. Security Properties Actually Achieved

- **Confidentiality at Rest**: Files are heavily encrypted at rest in `.pfce` packages.
- **Non-Repudiation**: Sender identity is strictly bound to the file hash via client-side RSA-PSS signing.
- **Forward Secrecy**: Receiver decryption keys utilize one-time prekeys to protect past transfers from future key compromise.
- **Active Threat Mitigation**: The server is able to successfully scan for malware and classify data *because* it intercepts the plaintext within a trusted enclave prior to encryption.

# 9. Threat Model

- **Compromised Network**: Protected by TLS.
- **Compromised Storage**: Protected by PFCE. Attacker cannot decrypt without the receiver's private key.
- **Compromised Database**: Protected. Attacker cannot decrypt the `.pfce` files using only database metadata.
- **Compromised FastAPI Server (Memory Dump / Kernel Access)**: **VULNERABLE**. An attacker with runtime access to the FastAPI server can intercept the plaintext uploads before they are scanned and encrypted.

# 11. Remaining Limitations

- True End-to-End Encryption is fundamentally incompatible with the server-side ClamAV and AI classification architecture currently deployed.
- Node.js temporary file storage (`os.tmpdir()`) briefly holds plaintext on disk before it is streamed to FastAPI. While `safeUnlink` is used, unexpected crashes could leave orphaned plaintext fragments on the API gateway's disk.

# 12. Final Thesis-Safe Statement

"The developed prototype employs a server-mediated encrypted file-transfer architecture. Client-side cryptographic signing provides sender attribution, while the internal FastAPI security engine performs malware inspection, behavioural security analysis, PFCE processing and receiver-specific cryptographic protection. Because the trusted security engine processes plaintext during selected stages of the transfer workflow, the architecture is not classified as strict end-to-end or zero-knowledge encryption."

# 13. Final Viva-Safe Statement

**30-Second Answer:**
"The system is not strict E2EE because the trusted FastAPI security engine processes plaintext for malware scanning and policy enforcement. Instead, it uses a server-mediated encrypted-transfer model with client-side signing and receiver-specific cryptographic protection."

**1-Minute Answer:**
"While the system employs advanced cryptographic features such as hybrid PQC, ECDH forward secrecy, and RSA-PSS signatures, it operates on a server-mediated trust model rather than strict Zero-Knowledge E2EE. When a file is uploaded, the sender's browser digitally signs it, but does not encrypt the content. The plaintext is transmitted over TLS to the FastAPI security enclave, where it is scanned by ClamAV and our AI behavioral models. Only after passing these checks is the data encrypted at rest into polymorphic PFCE fragments. This design prioritizes active threat mitigation over server blindness, which is a necessary trade-off for enterprise environments requiring centralized malware inspection."
